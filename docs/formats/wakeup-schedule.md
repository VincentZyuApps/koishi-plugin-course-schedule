# WakeUp 课程表规范、接口逆向与商业人性博弈 (WakeUp Schedule)

本插件原生支持通过 **WakeUp 课程表** 的「分享口令」与「`.wakeup_schedule` 备份文件」导入课表。
本文档详细记录了 WakeUp 的接口交互协议、多语言请求实现，以及商业收购后那场微妙的人性博弈。

## 🔑 一、分享口令 (Share Key) 机制与解析流程

### 1.1 分享文本与口令特征
在 WakeUp 课程表 App 中点击分享时，生成的经典文本如下：

```text
这是来自「WakeUp课程表」的课表分享，30分钟内有效哦，如果失效请朋友再分享一遍叭。
为了保护隐私我们选择不监听你的剪贴板，请复制这条消息后，打开App的主界面，
右上角第二个按钮 -> 从分享口令导入，按操作提示即可完成导入~分享口令为「a02b3a50f6a74fa49ec592597cef8162」
```

- **口令格式**：32 位十六进制字符串（通常为 MD5 或 UUID 变体哈希）；
- **生命周期**：服务端 Redis 缓存默认保留 30 分钟（过期自动丢弃并回收键值）；
- **鉴权特征**：v1 旧版属于纯粹的匿名 Key-Value 映射，无需任何 User Token 鉴权凭证。

### 1.2 插件正则提取规则
插件内部使用以下正则进行智能多重捕获，即使消息前后被用户添加了额外修饰词亦可精准提取：
- `分享口令为[「"'"]?([a-zA-Z0-9]+)[」"'"]?`
- `口令[：:]\s*([a-zA-Z0-9]+)`
- 独立 32 位 Hex 字符散列值

### 1.3 请求接口与网络协议细节
- **请求方法**：`GET`
- **请求 URL**：`https://i.wakeup.fun/share_schedule/get?key={shareKey}`
- **核心 Headers 伪装**：
  ```http
  User-Agent: okhttp/4.12.0
  ```

> ⚠️ **技术细节**：WakeUp 网关对客户端指纹有严格校验。非 Android 原生 OkHttp 特征的请求，
> 会直接被反爬规则阻断或返回 HTML 告警页。请求头必须携带原生请求特征才能调用 v1 接口。

### 1.4 多语言请求代码示范
各语言在调用时均需显式伪造请求头，否则会被网关判定为恶意爬虫直接拦截：

#### 1) Bash (cURL)
```bash
curl -s -X GET \
  -H "User-Agent: okhttp/4.12.0" \
  "https://i.wakeup.fun/share_schedule/get?key=a02b3a50f6a74fa49ec592597cef8162"
```

#### 2) JavaScript (Node.js 原生 https)
```javascript
const https = require('https');
const key = 'a02b3a50f6a74fa49ec592597cef8162';

const options = {
  hostname: 'i.wakeup.fun',
  path: `/share_schedule/get?key=${key}`,
  headers: { 'User-Agent': 'okhttp/4.12.0' }
};

https.get(options, (res) => {
  let raw = '';
  res.on('data', chunk => raw += chunk);
  res.on('end', () => {
    const json = JSON.parse(raw);
    console.log('Status:', json.status);
    if (json.data) console.log('Payload:', JSON.parse(json.data));
  });
}).on('error', err => console.error(err));
```

#### 3) Python (Requests)
```python
import json
import requests

key = "a02b3a50f6a74fa49ec592597cef8162"
url = f"https://i.wakeup.fun/share_schedule/get?key={key}"
headers = {"User-Agent": "okhttp/4.12.0"}

response = requests.get(url, headers=headers, timeout=15)
res_data = response.json()
print("API Status:", res_data.get("status"))
if "data" in res_data and isinstance(res_data["data"], str):
    schedule_info = json.loads(res_data["data"])
    print("Table Name:", schedule_info.get("tableName"))
```

### 1.5 API 响应结构与字段映射
在正常状态下，接口返回标准的 JSON 报文，其中核心负载为转义的 JSON 字符串：

```json
{
  "status": 1,
  "data": "{\"tableName\":\"2026秋\",\"startDate\":\"2026-09-07\",\"courseList\":[...],\"timeList\":[...]}",
  "message": "success"
}
```

顶层 `data` 字符串由插件二次反序列化为内部对象并进行数据库字段映射：

| 原始字段名 | 数据类型 | 字段含义说明 | 插件内部映射与持久化处理 |
| :--- | :--- | :--- | :--- |
| `tableName` | `string` | 课表名称 | 记录为课表元数据备注 |
| `startDate` | `string` | 学期开学日期（YYYY-MM-DD） | 作为本用户课表基准开学日，推算当前周数 |
| `courseList` | `array` | 课程明细记录数组 | 遍历后批量存入 `course_schedule` 数据表 |
| `courseList[].courseName` | `string` | 课程名称 | 映射写入 `curriculumname` |
| `courseList[].day` | `number` | 星期几（1 为周一，7 为周日） | 映射写入 `curriculumday` |
| `courseList[].room` | `string` | 上课教室与地点 | 映射写入 `curriculumposition` |
| `courseList[].teacher` | `string` | 任课教师姓名 | 映射写入 `teachername` |
| `courseList[].startNode` | `number` | 当天起始上课节次 | 结合 timeList 计算精确的起始时间点 |
| `courseList[].step` | `number` | 该节课程连续节数 | 结合 startNode 确定大节的持续时长 |
| `courseList[].stepWeekList` | `number[]` | 活跃周数列表（如 [1..16]） | 严格用于判断特定日期该课程是否实际上课 |
| `timeList` | `array` | 节次作息时刻表 | 用于将 `startNode`/`step` 转换为真实时刻 |

## 💾 二、备份文件 (`.wakeup_schedule`) 离线规范

除了在线口令，WakeUp 亦支持通过本地文件进行导出与还原。
该文件虽然以 `.wakeup_schedule` 命名，但本质上是**以换行符分隔的多段独立 JSON 文本**：

```text
Line 1: 头部元数据（版本标识号与保留字校验字段）
Line 2: 课表主表描述（包含 startDate 开学基准日与 tableName 表名）
Line 3: 全部课程数组（courseList，包含全部课程基础信息与上课周数）
Line 4: 各节次作息定义（timeList，包含每节课 node 编号及其起止时间）
Line 5: 客户端个性化配置（背景图路径、格子透明度、字体大小等显示设置）
```

插件内置的 `wakeup-file-parser.ts` 实现了对该备份格式的行级流式解析，
即使在断网或官方服务器宕机的极端情况下，亦可实现 100% 离线导入。

## 🎭 三、商业收购下的人性博弈与生存法则

很多同学会好奇：**WakeUp 后来被商业收购了，App 塞满广告还诱导开会员，为什么老版本（6.0.x）的分享口令接口至今还在稳定运行？**
甚至在 GitHub 与 Gitee 上长期公开挂着 6.0.23 的 APK 归档，也从未收到过任何 DMCA 侵权投诉。
这绝非资本发了善心，而是由**资本家老板、打工人码农、学生用户**三方的博弈构成的生动图景：

### 3.1 三重视角博弈矩阵分析
为了更直观地理解为何旧版口令接口能长期存活，我们可以将三方的动机与行为拆解为博弈矩阵：

| 角色视角 | 核心利益诉求 | 实际行为特征 | 对老版本（6.0.x）的真实心理 |
| :--- | :--- | :--- | :--- |
| **资本家老板** | 流量变现、商业闭环、追求最大化商业 ROI | 默认新版上架应用商店，加弹窗推会员 | (😅) 只要 90% 普通用户在看广告就行，不值得花法务成本去封杀小众极客 |
| **打工人码农** | KPI 考核达标、系统别崩、准点安全打卡下班 | 实施“防御性懒政”，非必要不碰祖传代码 | (🤡) 只要老接口不报警就继续留着，谁主动去关老接口导致客诉谁背大锅 |
| **学生用户** | 快速导入课表、无广告干扰、纯粹看课表 | 小白默默被应用商店自动更新，极客挖掘旧版 | (😏) 6.0.23 是最后的白月光，只要旧接口还能苟住，大家就各退一步不掀桌 |

### 3.2 资本家老板的心理：温水煮青蛙，最怕把锅掀了
- **大学生群体的特质**：手里没多少钱，但有极其充沛的精力与强大的社媒舆论扩散力；
- **拔苗助长的风险 (😅)**：若一上来就强制停服老接口并弹窗逼费，贴吧、知乎、酷安和应用商店一夜之间会被一星差评彻底冲烂；
- **商人的概率算计**：靠开学换新机和应用商店闲时静默更新，90% 的普通学生不知不觉就会成为广告受众。剩下的极客用户爱找旧版就找去，两边各取所需。
- **法务投诉的 ROI 考量 (🤡)**：向跨国开源社区发起侵权诉讼需要高昂流程成本，既然不伤及核心盘，何必多此一举？

### 3.3 打工人码农的心理：多一事不如少一事
- **祖传代码的沉重**：接手团队面对的是前人留下的遗留系统，谁也不知道老接口连接了多少所高校的内部缓存；
- **收益与风险严重失衡**：停掉老接口省不下几包泡面钱的服务器费，万一造成批量报错就是线上 P0 事故；
- **发 DMCA 投诉同样要花成本**：法务与研发在日常 KPI 驱动下，没人会吃饱了撑的跨国去举报 GitHub 上那几个冷门 Releases 仓库；
- **防御性懒政是最好的护甲 (☕)**：只要老接口没挂，就让它在服务器角落静静地躺平，大家都按时打卡下班。

### 3.4 学生用户的心理：实用主义与极客自救
- **小白用户的被动驯化**：大部分普通同学对 App 升级不敏感，弹广告就看，久而久之习惯了商业化改版；
- **硬核极客的反抗与自救 (😏)**：作者当年知道商业化改版后甚至想过亲自手搓开源替代品，但本着“能用且懒”的极客实用主义，退回 6.0.23 接着奏乐接着舞；
- **动态平衡的形成**：只要 6.0.23 还能喘气，极客们有后路可退，就不会耗费精力去跟官方硬碰硬搞对抗。

### 3.5 状态码 `5000004` 的黑色幽默
当我们使用新版（6.5.x）生成的口令去请求旧版接口时，服务端会返回一句极具讽刺意味的回执：

```json
{
  "status": 5000004,
  "message": "当前版本过低，请升级",
  "data": {}
}
```

- **黑色幽默的根源 (😅)**：老接口遇到了来自未来新协议的数据结构，由于无法识别，反过来嘲弄发起端“版本过低”；
- **防御性甩锅哲学 (🤡)**：系统一旦处理不了，第一反应就是指责客户端老旧，完美展现了经典的人性甩锅心理学。

### 4.2 防“背刺”指南：关闭系统应用商店自动更新
许多同学经常困惑“明明昨天才装了旧版，怎么一觉醒来又被升级成广告版了”？
根源在于各大安卓定制系统（MIUI/HyperOS/EMUI/ColorOS/OriginOS等）默认启用了夜间 Wi-Fi 闲时无感静默更新。

1. 打开系统自带的「应用商店」或「应用市场」；
2. 点击「我的」或头像区域，进入「设置」选项；
3. 找到「自动更新应用」或「WLAN下自动安装更新」，果断将其**关闭**；
4. 在应用更新检查列表中找到「WakeUp课程表」，长按或点击展开，勾选**忽略此版本更新**。

### 4.3 常见排错与导入问答 FAQ

- **Q1：为什么刚生成的分享口令立即绑定却提示已失效？**
  - A：WakeUp 服务端缓存口令时间为严格的 30 分钟。超过 30 分钟未绑定，Redis 键值将自动过期被清除，需在 App 内重新生成。

- **Q2：为什么抓包拿到的响应有时会返回 403 阻断？**
  - A：WakeUp 官方网关开启了严密的反爬防护。请求时务必伪装 User-Agent 为 `okhttp/4.12.0`，缺失请求头会被判定为恶意爬虫。

- **Q3：手机上同时安装新旧版会产生冲突吗？**
  - A：由于二者包名完全一致，无法直接共存。建议卸载新版本后直接全新安装 6.0.23 稳定版，首次打开切记拒绝应用内更新提示。

- **Q4：如果以后老接口真的彻底下线了怎么办？**
  - A：无需惊慌，插件已完整实现 `.wakeup_schedule` 本地备份文件解析以及 Yunzai 原生 JSON 解析，支持双重离线灾备。

- **Q5：WakeUp 导出的周数和教务不一致怎么办？**
  - A：可以在 WakeUp 设置中手动校准开学日期（第一周周一），然后再重新生成分享口令导入。

- **Q6：iOS 用户可以使用 6.0.23 吗？**
  - A：iOS 无法像安卓一样轻松降级。iOS 用户建议找安卓室友帮忙导课生成口令，或直接使用 Yunzai 原生 JSON。

- **Q7：为什么我的口令提取失败？**
  - A：请检查口令格式是否完整，口令字符串必须为 32 位 Hex 字符，避免在复制过程中丢漏前导或尾部字符。

- **Q8：导入后发现部分课程时间重叠？**
  - A：可能是由于学校教务系统在同一时间段排有多门单双周课程，插件会在渲染周视图时自适应分列排版。

- **Q9：口令接口的响应延迟通常在什么范围？**
  - A：由于直接走 Redis 读取，服务器响应极快（通常在 100ms~300ms 之间），若长时间未响应多为本地网络波动。

- **Q10：如何彻底避免 App 在后台被系统应用市场静默偷跑更新？**
  - A：除了在商店关闭自动更新，亦可在应用信息页面关闭其「允许后台联网安装应用」系统权限。

- **Q11：导入后的课表在不同设备间能同步吗？**
  - A：课表数据保存在 Koishi 宿主数据库中，只要在同一群聊或通过同一个用户账号查询，均可实时读取。

- **Q12：6.0.23 的备份文件能否与新版 App 互通？**
  - A：实测向下兼容良好。新版导出的 `.wakeup_schedule` 文本结构未有破坏性变更，6.0.23 及本插件均可正常识别。

- **Q13：为什么学生明明讨厌广告，但大多数人最终还是被商业版妥协收割了？**
  - A：因为绝大多数人的本质是“路径依赖”与“信息壁垒”。能折腾旧版、找 APK、逆向协议的极客永远是极少数；学业生活早已耗尽了普通人的精力，资本正是利用人性的疲惫与惰性，用一次无感的静默更新，完成了对大多数人的收割。
